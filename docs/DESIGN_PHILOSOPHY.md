# 狐嗦粤语 — 设计宗旨 (DESIGN PHILOSOPHY)

> 本文档是项目的"宪法"。所有玩法设计、技术架构、开发决策必须以此为准绳。
> 与其他文档冲突时,以本文档为准。
> 修改本文档需谨慎,需与产品方向共同确认。

---

## 一、核心定位

**这是一款游戏,不是学习软件。学习是顺便的。**

传统"教育游戏"的根本问题:打着游戏的幌子做学习软件,学习内容强行插入,破坏游戏体验,用户玩几次就腻。

我们的解法:**先做好玩的游戏,学习在玩家享受游戏的过程中自然发生。**

判别标准:如果把粤语学习内容全部抽掉,这款游戏本身是否还值得玩?如果是,设计成立;如果不是,设计失败。

---

## 二、六大设计原则

### 原则1:游戏第一,学习第二

- 优先级永远:可玩性 > 学习性
- 当游戏体验与学习内容冲突时,让位给游戏体验
- 学习内容是游戏的"副产品",不是"目的"
- 评判任何功能:先问"好不好玩",再问"学没学到"

### 原则2:流畅性优先于精美性

- **点击/操作必须有即时反馈动效**(不需要精美,但必须有反馈)
- 严禁同步阻塞代码大量出现(避免卡顿破坏体验)
- 现阶段不要追求画面精美,关键在于流畅性与高可玩性
- 反馈层级:输入即时(<16ms)→ 动效反馈(100~300ms)→ 状态反馈(场景级)

### 原则3:铺垫链思路(核心创新)

**学习内容不是"蹦出来"的,而是玩家自己"拼出来"的。**

游戏中的所有物品、人物、场景、对话都是**铺垫**,共同指向最终要揭示的那一句粤语。

- 不是:角色蹦出来说一句台词
- 而是:玩家经历一系列关联元素,潜意识拼凑出梗的轮廓,最后难度完成时触发句子,产生"恍然大悟"的爽感

**铺垫链结构**:
```
碎片1 → 碎片2 → 碎片3 → ... → 难度挑战 → 句子揭示(所有碎片归位)
```

**判别标准**:揭示句子时,玩家脑中是否已经具备理解这句台词的所有关键词?如果是,铺垫链成立。

### 原则4:惊喜三段式叙事

惊喜事件不是"突然蹦出角色",而是有节奏的三段式:

| 阶段 | 作用 | 手法 |
|------|------|------|
| 铺垫 | 建立预期 | 全局提示卡片预告("3秒后会出现...") |
| 揭示 | 认知共鸣 | 伪图卡片显示角色/物件,文字滚动描述 |
| 互动 | 惊喜转玩法 | 角色对话转化为指引/buff/解锁 |

**惊喜来源**(类型要宽,不限文化梗):
- 文化梗(孙悟空/叶问/周星驰角色)
- 网络热梗
- 谐音梗
- 粤语本地文化符号
- 优先选**大众共鸣最强**的(如叶问"我要打十个" > 黄飞鸿)

### 原则5:伪图卡片系统(全局视觉组件)

现阶段不使用真实图片资源,采用**伪图卡片系统**作为通用视觉组件。

**核心理念**:用一个框 + 文字描述代替图片,后期可无缝替换真图。

**基础属性**:
- 文字内容(主文字 / 副文字)
- 文字颜色、字体
- 边框(颜色/粗细/样式)
- 背景色(支持高亮)
- 尺寸、缩放
- 后缀语义:`.jpg` 静态 / `.gif` 文字循环滚动(会心一笑的梗)

**全局复用**:同一个伪图卡片系统服务于
- 场景物件(咸鱼/石头/路标)
- 角色立绘(NPC/主角)
- 对话卡片
- 提示卡片(全局提示)
- 结算卡片

**扩展性**:预留接口,方便后续给伪图卡片添加功能(动画类型/特效/交互响应)。

**长期价值**:可能省去后期大量图片资源,游戏加载更快、性能更好、操作更流畅、代码更简洁,形式新奇有趣反而能吸引用户。

### 原则6:反向引导机制

**伪图卡片的文字提示不是装饰,而是可互动的引导信号。**

- 负面提示("别碰""禁止")反而激发玩家探索
- 玩家"反骨"碰了,必有反馈(以奖励为主,弱惩罚)
- 让"反骨探索"成为乐趣来源,而非挫败来源

**示例**:咸鱼伪图卡片滚动"别碰我..." → 玩家碰了 → 咸鱼弹开撞破墙 → 露出隐藏区域。

## 三、对话语言规则

**全程普通话对话,只有最终揭示的目标句子是粤语 + 发音。**

- NPC 对话、剧情对话、提示文字:普通话(降低认知负担)
- 铺垫链中的关键词:可以是普通话,也可以是粤拼(视情况)
- 最终揭示的句子:粤语原版 + 粤拼 + 普通话释义 + 发音

**理由**:让粤语成为"揭示时刻",而非全程的认知负担。玩家在普通话铺垫中建立理解,最终粤语揭示时产生"原来这样说"的爽感。

## 四、可扩展性原则(务实扩展)

**初赛 Demo 专注一个关卡,但核心组件保持可扩展性。**

### 核心理念

不为"扩展"而扩展,不为"通用"而通用。**宗旨是游戏可玩**,不被"扩展性"限制死。

### 三条原则

1. **核心组件可扩展即可**
   - 伪图卡片系统(TextSprite)、发音引擎(SpeakerManager)、惊喜事件、Buff 系统、Player 等核心组件设计时预留扩展点
   - 不要求所有关卡用同一套数据模型驱动
   - 不为"零代码加关卡"这种目标做过度抽象

2. **关卡/人物/场景可自由定制**
   - 每个关卡可以有独立的关卡文件/组件/脚本,不强求统一模板
   - 每个人物、场景可以有独特逻辑,不强求 JSON 化
   - 关卡数据(位置/文本/配置)能用 JSON 描述就用 JSON,不能就用代码,不强求

3. **游戏可玩优先**
   - 当"扩展性"与"快速做出来好玩"冲突时,优先做出来好玩
   - 复杂逻辑直接写代码,不硬塞 JSON
   - 不过度设计,初赛 Demo 聚焦把第一关跑通跑好玩

### 判别标准

- ✅ 核心组件(TextSprite/Speaker/Player 等)能复用到第二关且不改源码 → 架构成立
- ✅ 第一关的独特逻辑写在第一关自己的文件里,不污染核心 → 架构成立
- ❌ 加第二关时必须改核心组件源码才能跑 → 架构需优化(但不强求避免)

**底线**:初赛阶段以"做出好玩的 Demo"为第一目标,扩展性是加分项不是必答题。

## 五、开发工作流

1. **文档先行**:任何功能开发前,先在对应文档(LEVEL_DESIGN/GAME_DESIGN/TECH_ARCH)写清设计
2. **思路确认**:复杂改动先与产品确认思路,再实现
3. **实时更新文档**:开发过程中文档与代码同步,文档不许"过期"
4. **常回顾宗旨**:每次开发前回顾本文档,确保不偏离核心理念
5. **进度可追溯**:TASKS.md 跟踪任务状态,DEVLOG.md 记录决策与变更
